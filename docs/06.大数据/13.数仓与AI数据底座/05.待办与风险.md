# 待办与风险

> 这一页是评审视角：哪些结论可以直接用，哪些表述需要修正，哪些设计还没闭环。
> 拍板前先看这里，比看 26 页幻灯片快。

## 总体判断

**方案成立，可以作为建设依据。** 五层划分、唯一持久层、开放表格式 + 开放目录、批流分工、全开源可私有化，这几条主线是自洽的，也符合 2026 年的技术现实。

但有 **3 类问题**需要在开工前处理：

1. **事实性表述**有 4 处需要修正，否则知识库会传播错误结论；
2. **设计缺口**原有 5 个：SQL 网关、容量模型、HA/DR、权限执行点、Iceberg 维护——其中 SQL 网关与 HA/DR 已补方案，其余仍待拍板；
3. **测试集群的边界**要提前说清，避免把"3 节点跑通"当成生产验收。

## 一、需要修正的表述

| # | 原表述 | 问题 | 建议表述 |
| --- | --- | --- | --- |
| 1 | Airflow "没有图形化界面，需要写代码" | Airflow 有完整的 Web UI；真正的差异是 **DAG 用 Python 代码定义**，改流程要改代码发版 | "Airflow 有 Web UI，但 DAG 以代码定义；DolphinScheduler 是可视化拖拽，业务人员可自助改流程" |
| 2 | Greenplum "社区版本已经维护了" | 应为"已停止维护"（笔误，语义反了） | "Greenplum 社区版已停止维护" |
| 3 | Vault "改成了闭源许可" | Vault 改为 **BUSL**，源码可见，但不是 OSI 开源 | "Vault 改为 BUSL 源码可见许可，不再是 OSI 开源，故选 OpenBao" |
| 4 | "全部组件免费、无授权与订阅费用" | 软件许可免费成立，但 Grafana / Loki / Alloy / Elasticsearch 是 **AGPL**，对外交付产品时有分发义务 | "软件许可免费；AGPL 组件内部使用无分发义务，对外交付需法务复核" |

另外两处措辞建议软化，避免被挑战：

- "HDFS 已经过时" → "HDFS 仍是存量系统的主流，但新湖仓默认选对象存储，因为存算解耦"。
- "ClickHouse 多表关联弱" → "ClickHouse 在单表扫描上极强，临时多表 JOIN 的体验不如 MPP，且运维负担重"。

## 二、设计缺口

| # | 缺口 | 严重度 | 现状 | 建议 |
| --- | --- | --- | --- | --- |
| 1 | **SQL 取数网关没有选型** | P0 | 原稿只有"受控网关"概念，Envoy Gateway 只能管 HTTP，管不了 JDBC 的脱敏与行级过滤 | **已补方案**：不引入独立 SQL 代理；BI 走 Doris 内置 RBAC，临时分析走 Kyuubi + Ranger，应用走 REST 取数 API。详见[查询与治理](02.选型决策/04.查询与治理.md) |
| 2 | **容量与成本模型缺失** | P0 | 26 页全是定性对比，没有 TB、IOPS、副本系数、带宽的账 | 按"原始数据量 × 副本系数 × 1.3"估存储；按峰值并发估 Doris BE；按日增量估 Kafka |
| 3 | **HA / DR 没有设计** | P0 | 原稿只说"K8s 自愈"，没说 RPO/RTO、Ceph 故障域、PG 备份、跨机房 | **已补页面**：[高可用与容灾](03.部署实施/03.高可用与容灾.md) 给出 HA 清单、备份矩阵、RPO/RTO 分级 |
| 4 | **三段权限的执行点没落** | P0 | "身份 → 表级 → 行列级"讲了三段，但没说谁执行 | 身份：OIDC/LDAP；表级：Polaris + Doris；行列级：Doris policy / Ranger / API 字段白名单 |
| 5 | **Iceberg 维护没排期** | P1 | 小文件、快照、孤儿文件没有 owner | 用 DolphinScheduler 建三个日/周任务，纳入监控 |
| 6 | **升级与兼容矩阵** | P1 | 组件版本没锁定 | 锁定 K8s、Operator、引擎三条版本线，升级前跑兼容测试 |
| 7 | **多租户与配额** | P1 | 说了多租户，没有项目/队列/资源组设计 | 按业务域分 namespace + ResourceQuota + Doris 资源组 |
| 8 | **数据分类分级与保留** | P1 | 提了 WORM，没说哪些数据要锁、锁多久 | 先盘行业合规与内部制度要求，再定 bucket 与保留策略 |
| 9 | **SLO 与告警阈值** | P2 | 有监控组件，没有目标值 | 先定三个：入湖 freshness、查询 P99、平台可用性 |

## 三、风险登记

| 风险 | 可能性 | 影响 | 应对 |
| --- | --- | --- | --- |
| 三台资源释放后要重搭 | 高 | 中 | 环境即代码：bootstrap 脚本 + values 进 Git；每阶段快照；测试数据用固定 seed 重建 |
| 三台不在同一内网 / 私网不通 | 中 | 高 | 下单前确认同 VPC、私网互通；安全组放行 etcd/flannel/kubelet 端口 |
| 镜像拉取慢导致当天搭不完 | 高 | 中 | 选 100M 带宽；三台并行拉；提前列镜像清单 |
| Ceph 数据盘已格式化，OSD 起不来 | 中 | 中 | 下单前确认裸盘；不行就 SeaweedFS，Iceberg 路径不变 |
| 内存不足，组件互相 OOM | 中 | 中 | 每台 32G；JVM 统一设 `-Xmx`；治理层后置 |
| SQL 网关方案落地偏差 | 中 | 高 | 按"BI 走 Doris / 分析走 Kyuubi / 应用走 REST"分工；POC 不开外网 JDBC |
| 一天时间不够 | 高 | 中 | 拆两次会话；第一次只做 P0–P4；或买 2–3 天 |
| 组件版本不兼容（Spark/Iceberg/Polaris） | 中 | 高 | 用官方兼容矩阵，先跑最小冒烟，再上测试数据 |
| 公网暴露被扫 | 中 | 中 | 只开 22、禁密码登录、fail2ban；用完释放或关安全组 |

## 四、开工前的 6 个决定

1. **集群形态**：3 × 32C32G（推荐，先买 3 台，可在线加到 5）还是 5 × 32C32G（¥40/天）？不建议 5 × 16G。
2. **存储**：SeaweedFS 3 节点（快）还是 Rook + Ceph（真实、慢）？
3. **时长**：1 天、2 天还是 3 天？建议拆成两次 3–4 小时会话。
4. **SQL 网关**：接受"BI 走 Doris、分析走 Kyuubi、应用走 REST"这套分工吗？
5. **数据**：合成数据（推荐，固定 seed）还是脱敏样本？
6. **交付物**：只要"跑通截图"，还是要一套可复用的 `deploy/` 脚本 + values？

## 五、建议的推进顺序

```
评审修正（本文） → 定集群/存储/时长 → 买 3 台 → 三节点体检
   → kubeadm 三节点（CNI + 3 节点 Ready）
   → 存储 + 目录（SeaweedFS + PG + Polaris + Iceberg）
   → 计算 + 查询（Kafka 3 + Doris 3FE/3BE）
   → 调度 + 治理（可后置）
   → 端到端 + 导出/快照 → 回填知识库
```

地基是 **S3 + Polaris + Spark 写 Iceberg**。这条线不通，上面装得再多也是白装；建议第一次会话只保证这条线跑通，其余算加分项。
