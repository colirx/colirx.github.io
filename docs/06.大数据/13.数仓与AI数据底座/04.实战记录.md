### 镜像分发（实测结论）

| 方式 | 速度 | 适用 |
| --- | --- | --- |
| `docker.1ms.run` 直接拉 | 1.3 MiB/s（cni 68MB/52s），大镜像会降到 0.4MB/s | 小镜像、少量节点 |
| node1 `scp` 到 node2/3 + `ctr import` | 219MB tar 几秒到十几秒 | **大镜像批量分发首选**，同网段 |
| Windows 中转 | 慢且多一跳 | 不推荐 |

- containerd 配置：`/etc/containerd/certs.d/docker.io/hosts.toml` 里 `server = "https://docker.1ms.run"`，不要写 `registry-1.docker.io`，否则先连官方源超时。
- **`:latest` 的坑**：默认 `imagePullPolicy: Always`，即使本地有镜像也会强制回源，表现为 `ImagePullBackOff`。测试镜像要么用固定 tag，要么显式 `IfNotPresent`。
- 已在 node1 生成节点间密钥，node2/3 的 `authorized_keys` 已加入，可直接 `scp` 分发镜像 tar。

### 关键命令（可复现）

```bash
# containerd 配置
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sed -i "s#sandbox = '.*'#sandbox = 'registry.aliyuncs.com/google_containers/pause:3.10.2'#" /etc/containerd/config.toml
systemctl restart containerd

# K8s 包（阿里云源）
curl -fsSL https://mirrors.aliyun.com/kubernetes-new/core/stable/v1.37/deb/Release.key \
  | gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://mirrors.aliyun.com/kubernetes-new/core/stable/v1.37/deb/ /' \
  > /etc/apt/sources.list.d/kubernetes.list
apt-get update && apt-get install -y kubelet kubeadm kubectl
apt-mark hold kubelet kubeadm kubectl

# 预拉控制面镜像（关键：不要用默认 registry.k8s.io）
kubeadm config images pull \
  --image-repository=registry.aliyuncs.com/google_containers \
  --kubernetes-version=v1.37.1

# 初始化控制面
kubeadm init \
  --apiserver-advertise-address=<node1-ip> \
  --control-plane-endpoint=<node1-ip> \
  --pod-network-cidr=10.244.0.0/16 \
  --kubernetes-version=v1.37.1 \
  --image-repository=registry.aliyuncs.com/google_containers \
  --cri-socket unix:///run/containerd/containerd.sock
```

### 镜像源结论（本次踩坑）

| 源 | 结果 | 结论 |
| --- | --- | --- |
| `registry.k8s.io` | 302 到 Google `pkg.dev`，连接超时 | **不可用**，kubeadm 必须加 `--image-repository` |
| `registry.aliyuncs.com/google_containers` | kube-apiserver 29.8MB / 5.9s | **K8s 控制面首选** |
| `ghcr.io` | API 401 可达，但多架构 index 拉取极慢 | Flannel 放弃，不推荐 |
| `ghcr.nju.edu.cn` | `/v2/` 200，拉取仍逐个解析多架构 manifest | 能通但慢 |
| `docker.m.daocloud.io` | Docker Hub 401 可达 | 可用，速度约 0.9–1 MB/s |
| `docker.1ms.run` | `/v2/` 401；`calico/cni` 68.6MB / 52s（1.3 MiB/s） | **Docker Hub 首选**，实测最稳 |
| `dockerproxy.net` | `/v2/` 200；同一镜像可复用层 | 备选 |
| `wget.la` / `proxy.vvvv.ee` | `/v2/` 200 | 备选 |
| 华为 SWR 个人镜像地址 | `/v2/` 401 | 需账号认证，未用 |

**最终 containerd 配置**（三台一致）：

```toml
# /etc/containerd/certs.d/docker.io/hosts.toml
server = "https://docker.1ms.run"
[host."https://dockerproxy.net"]
  capabilities = ["pull", "resolve"]
```

> 关键点：`server` 直接写镜像地址，不要写 `registry-1.docker.io`。否则 containerd 会先连官方源，国内超时后才考虑 host，表现为 `ImagePullBackOff`。
> 已经手工拉过的镜像，用 `ctr -n k8s.io images tag <mirror>/... docker.io/...` 打成标准名，kubelet 就直接用本地镜像。

> 教训：`ctr images pull` 对多架构 index 即使加 `--platform linux/amd64` 也会解析所有 manifest，ghcr 镜像尤其慢；能用单镜像/国内仓库就别用 ghcr。

### Kafka（K8s，已跑通）

- Strimzi Helm chart 在 GitHub Releases 下载超时，改为**手工 StatefulSet**；镜像 `apache/kafka:3.9.0` 从 daocloud/1ms 拉取后 LAN 分发到 3 节点。
- **KRaft 最大的坑**：`CONTROLLER://0.0.0.0:9093` 会被 Kafka 当作 advertised listener 校验，报
  `advertised.listeners cannot use the nonroutable meta-address 0.0.0.0`。
  正解：`CONTROLLER` listener 和 `advertised.listeners` 都用 **Pod IP**；Pod 内 `hostname -I` 在 BusyBox 下不支持，改用 Downward API 注入 `status.podIP`。

### P6：MySQL CDC → Flink → Kafka → Iceberg（已跑通）

- **MySQL 进 K8s**：StatefulSet + 10Gi local-path，ConfigMap 写 `server-id/log-bin/ROW/FULL/GTID`，Service `mysql.data:3306`；`flink` 用户授予 `SELECT, REPLICATION SLAVE, REPLICATION CLIENT`。
- **Flink 进 K8s**：官方 `flink:1.20.5` 镜像拉取长时间卡住，改用**已在所有节点的 `apache/kafka:3.9.0` 当 Java 运行时**，hostPath 挂 node1 的 `/opt/flink`（含 connector），JM/TM 都是 K8s Pod。
- Flink 三个关键坑：
  1. `FLINK_PROPERTIES` 只对官方镜像的 entrypoint 生效，直接跑 `taskmanager.sh` 不读；要写 `conf/flink-conf.yaml`（`jobmanager.rpc.address: flink-jobmanager`、内存配置）。
  2. JM 的 **blob server 默认随机端口**，TM 下载任务包会一直卡在 `DEPLOYING`；固定 `blob.server.port: 6124` 并在 Service 暴露 6124。
  3. 不开启 checkpoint 时增量 binlog 不接；SQL 里加 `SET 'execution.checkpointing.interval'='10s'` 后，插入 id=3/id=4 都能进 Kafka。
- **Flink Iceberg connector 1.7.1 不支持 `catalog-type=jdbc`**（只支持 hive/hadoop/rest），Polaris REST 又受 STS 阻塞；因此 **Kafka→Iceberg 暂用宿主机 Spark**（JDBC catalog + S3FileIO）。
- 验证结果：Kafka `cdc.orders` 有快照 2 条 + 增量 id=3/4；Spark 读 Kafka 写入 `lake.ods.cdc_orders`，`total=6, distinct id=4`，rc=0。
- 查询验证：Spark SQL `SELECT * FROM lake.ods.cdc_orders ORDER BY id` 返回 6 行（id 1–4），`count(*)=6, count(distinct id)=4`。

### Doris（部署中）

- 安装 `doris/doris-operator` **25.8.0** 到 `doris` namespace，CRD `DorisCluster` 就绪。
- 创建 `DorisCluster doris`：**1 FE + 1 BE**（先验证 SQL，再考虑扩 3FE/3BE），镜像 `apache/doris:fe-4.1.0-slim` / `be-4.1.0-slim`。
- 持久化：FE `doris-meta` 20Gi、BE `storage` 50Gi，均 `local-path`。
- FE 镜像约 1.0GB、BE 1.5GB，国内源拉取很慢；FE Pod 已 Running，9030 端口 `SHOW FRONTENDS` 正常。
- BE 首次拉取出现 **layer digest 不一致**（多次断点续拉导致 content 损坏），kubelet `ImagePullBackOff`；后改为本地下载 1.5GB tar → 上传 node1 → `ctr import`（带解压约 9 分钟）成功。
- **最终根因不是镜像，而是 CPU 缺少 AVX2**：`/proc/cpuinfo` 只有 `avx`，型号 Xeon E5-2695 v2；BE 启动日志明确 `the host machine not support avx2 instruction set`，随后 `post_exit`，Pod 进入 `Completed`。Doris 官方运行时镜像没有 no-AVX2 变体（只有 `build-env-*-no-avx2` 构建环境），因此 **Doris BE 在这台服务器上无法运行**。
- 结论：Doris 查询链路需要 **支持 AVX2 的 CPU**，或改用 Trino/ClickHouse/Spark SQL 等不要求 AVX2 的查询引擎；当前服务器上 Doris 只能保留 FE，不能完成查询。
- **决策（2026-10-18）**：当前 CPU（E5-2695 v2）无 AVX2，Doris/StarRocks 均不满足运行条件，不纳入本次验收；查询层使用已验证的 **Spark SQL**。后续如需 OLAP，优先换 AVX2 机器，或在当前机器改用 ClickHouse/Trino。

### PostgreSQL CDC 验证（新云，2026-10-18）

- 目标：覆盖“公司只部署一个关系型数据库”的场景，验证 PostgreSQL 逻辑复制 CDC。
- PG 配置：`wal_level=logical`、`max_replication_slots=10`、`max_wal_senders=10`（通过 StatefulSet `args` 注入，重启后仍生效）。

### 镜像配置最终版（重要）

这是本次最关键的一处修复，**containerd 2.x 的官方推荐写法**（[hosts.md](https://github.com/containerd/containerd/blob/main/docs/hosts.md)）：

```toml
# /etc/containerd/config.toml
[plugins.'io.containerd.cri.v1.images'.registry]
  config_path = '/etc/containerd/certs.d'
```

```toml
# /etc/containerd/certs.d/docker.io/hosts.toml
server = "https://docker.1ms.run"
[host."https://dockerproxy.net"]
  capabilities = ["pull", "resolve"]
```

四个坑，缺一个都不生效：

1. `config_path` 必须是**单个目录**；写成 `/etc/containerd/certs.d:/etc/docker/certs.d` 会被整体忽略，仍然回 `registry-1.docker.io`。
2. `config_path` 和 `registry.mirrors` **不能同时设置**，否则 containerd 报 `mirrors cannot be set when config_path is provided`，CRI 插件直接加载失败，kubelet 起不来。
3. 目录名用 `docker.io`，不是 `registry-1.docker.io`。
4. `hosts.toml` 里把镜像写成 `server`，才会只走镜像；写成 `[host]` 会先试官方源，国内超时。

要求：

- **固定 seed**：每次重建数据一致，便于对比结果；
- **时间戳落在最近 30 天**：方便按天分区、测补数；
- **包含更新与删除**：验证 Iceberg 行级变更与 Doris 主键表；
- **数据量控制在 1 GB 以内**：测试盘只有 200–300G，别把集群写满。

生成脚本放 `deploy/smoke/gen_data.py`，随环境重建一起跑，不导入真实业务数据。

## 需要重点盯的坑（预判）

三节点比单机多出"网络、etcd、调度、副本"四类问题：

| 风险点 | 可能现象 | 预案 |
| --- | --- | --- |
| 私网不通 | node2/3 加入集群超时 | 先 `ping`/`nc 6443` 验证；安全组放行内网端口 |
| kubelet/CNI 选错网卡 | 节点注册到公网 IP，Pod 跨节点不通 | 显式 `--node-ip` / `IP_AUTODETECTION_METHOD` |
| etcd 只有 1 成员 | 挂了 node1 集群就不可用 | `etcdctl member list` 验证 3 成员 |
| 副本全挤一台 | Kafka/Doris "3 副本"形同虚设 | 配 `podAntiAffinity`，用 `kubectl get pods -o wide` 核对 |
| 镜像拉取慢/失败 | `ImagePullBackOff` | 配国内镜像加速；大镜像先 `docker pull` 再导入 |
| Pod 被 OOMKilled | JVM 组件反复重启 | 先设低 heap（`-Xmx`），再按实际调 limits |
| PVC 一直 Pending | local-path 没装或磁盘满 | 检查 StorageClass 与 `/data` 余量 |
| S3 endpoint 不通 | Iceberg 提交超时 | 用集群内 Service 名，不用公网 IP；确认 path-style |
| Polaris 建表 403 | 凭证或 allowedLocations 不匹配 | 核对 AK/SK、bucket 前缀、realm |
| Doris BE 起不来 | `ALIVE: false` | 看 BE 日志的 `storage_root_path` 与内存 |
| Flink checkpoint 失败 | 作业反复 restart | checkpoint 目录权限、S3 凭证、状态后端 |
| 时间不同步 | 证书/Token 校验失败 | 三台都先做 NTP，再装组件 |
| 磁盘写满 | 整个节点不可用 | 镜像保留策略 + 日志轮转 + 监控 85% 告警 |
| 实例释放后 IP 变 | kubeconfig/证书全失效 | 环境即代码，重建时重新生成 kubeconfig，别硬编码 IP |

## 后续复用

搭建完成后，会把可复用的部分抽出来：

- `values/`：每个组件的测试 values；
- `manifests/`：Kafka、Doris、Flink、Spark 的 CR 样例；
- `scripts/`：初始化、建库建桶、冒烟测试、数据生成；
- `export.sh` / `teardown.sh`：导出与清理。

这些文件是否进仓库、放在哪个目录，等搭建完再定——避免把一堆一次性脚本塞进知识库。
