# 多节点集群与低成本重建

> 前提：这是**个人测试**，按天买、随时可能释放、公共 IP 会变、数据可以不要。
> 目标：用最少的钱搭一个**真 K8s 集群**（不是单机 k3s），验证组件能跑通、调度/副本/选主机制有效；环境随时可以从零重建。

## 一、为什么必须是多节点

单机 k3s 能装完所有组件，但验证不了这个架构真正关心的东西：

| 能力 | 单机 | 3 节点 |
| --- | --- | --- |
| Pod 调度到不同节点 | ❌ | ✅ |
| 节点 drain / 维护 | ❌ | ✅ |
| Kafka 3 broker、RF=3、挂一个 broker | ❌ | ✅ |
| Doris 3 BE、副本分布 | ❌ | ✅ |
| Ceph 3 OSD、CRUSH、副本重平衡 | ❌ | ✅（裸盘可用时） |
| PG 主备切换 | ❌ | ✅ |
| K8s 控制面 etcd 选主 | ❌ | ✅ |

**"组件能启动"和"集群能工作"是两件事。** 多节点多花的钱（约 ¥9–16/天）买的就是后面这件事。

## 二、推荐拓扑

### 方案 A：真集群（推荐）

**3 台 32C32G / 300G 数据盘 / 50–100M，¥8/台/天，合计 ¥24/天。**

| 节点 | 角色 | 主要负载 |
| --- | --- | --- |
| node1 | kubeadm control-plane | Kafka-1、Doris FE-1（leader）、Doris BE-1、PG primary、SeaweedFS master-1、Polaris-1、DS master、Prometheus |
| node2 | kubeadm worker | Kafka-2、Doris FE-2、Doris BE-2、PG standby、SeaweedFS volume-2、Polaris-2、DS worker、Grafana/Loki |
| node3 | kubeadm worker | Kafka-3、Doris FE-3、Doris BE-3、SeaweedFS volume-3、DS worker、OpenMetadata/ES（可选） |

- 1 个 control-plane + 2 个 worker；测试期把 node1 的 `control-plane:NoSchedule` taint 去掉，让业务 Pod 也能跑上去，否则只有 2 台干活。
- Kafka、Doris、PG 用 **podAntiAffinity** 按节点打散，副本才有意义。
- 入口用 Envoy Gateway + NodePort，访问任意节点 IP 都行。

### 扩到 5 台（可选，不推荐一开始就买）

3 台跑起来后如果内存紧，或想演"5 节点调度 / 挂 2 台"，再补 2 台同型号即可，kubeadm 支持在线 join（token 有效期内），不用重建：

| 节点 | 角色 | 主要负载 |
| --- | --- | --- |
| node4 | kubeadm worker | Spark Executor、Flink TaskManager、DS worker |
| node5 | kubeadm worker | OpenMetadata + ES、Kyuubi、压测客户端 |

- 5 台的建议是 **5 × 32C32G**（¥40/天），不是 5 × 16G；后者总内存反而比 3×32G 少。
- 加节点后记得给 Kafka/Doris 扩副本或重分布，否则新节点只是"多了一台空闲机器"。

### 方案 B：极限省

**3 台 8C16G / 50G / 50M，¥5/台/天，合计 ¥15/天。**

- 只能跑核心链路：K8s + SeaweedFS + PG + Polaris + Kafka（1–3 broker）+ Doris（1 FE + 3 BE）+ Spark/Flink（按需）。
- 砍掉：OpenMetadata + ES、Kyuubi、Ceph、多副本。
- 50G 盘很紧：镜像约 20G，数据只能放很小；必须配镜像清理。
- 适合"只验证 K8s 和链路能通"，不适合验证 HA。

**建议**：如果预算能到 ¥24/天，选 A；A 的 32G/节点能让 Kafka/Doris/Spark 同时跑，不用一路 OOM 排障。省下的 ¥9 不值得多花半天。

## 三、采购的硬性要求

多节点和单机不一样，网络与磁盘不满足，集群直接搭不起来：

- [ ] **同地域、同 VPC / 内网互通**：三台能互相 ping 通私网 IP，这是 etcd 和 Pod 网络的前提。
- [ ] **每台有独立私网 IP**：节点用私网 IP 注册，别用公网 IP 跑 etcd。
- [ ] **安全组**：公网只开 22；节点之间放行 6443（API）、8472（flannel VXLAN）、10250（kubelet）、2379–2380（etcd）、30000–32767（NodePort，仅内网）。
- [ ] **数据盘**：每台 200–300G（方案 A）或 50G（方案 B）；如果要用 Ceph，数据盘必须能**不格式化**直接给 OSD 用。
- [ ] **系统盘**：≥40G，放 OS + 容器镜像；镜像别放数据盘（Ceph 要裸盘）。
- [ ] **带宽**：≥50M；3 台同时拉镜像，50M 约 1 小时，100M 约 30 分钟。
- [ ] **快照**：确认实例释放后快照是否保留——这决定下次是"恢复"还是"重建"。

## 四、存储怎么选（测试期）

| 方案 | 前提 | 搭建时间 | 能验证 | 建议 |
| --- | --- | --- | --- | --- |
| **SeaweedFS 3 节点** | 普通数据盘即可 | 30–40 分钟 | 分布式 S3、多节点读写 | **测试首选**，Iceberg 路径与 Ceph 完全一致 |
| **Rook + Ceph RGW** | 每台一块未格式化数据盘 | 1.5–2 小时 | OSD、CRUSH、3 副本、RGW | 想验证生产存储时再上；时间不够别硬上 |

SeaweedFS 的拓扑：master 3（Raft）、volume 3、filer 2、s3 2。它不是 Ceph 的替代品，但 S3 语义够 Iceberg 用，且不用赌云盘能不能裸用。

**PVC 从哪来，要和存储方案一起定**：

| 方案 | 数据盘用途 | PVC StorageClass | 系统盘 |
| --- | --- | --- | --- |
| SeaweedFS | 格式化挂 `/data` | local-path（落在 `/data`） | OS + 镜像 |
| Ceph | 裸盘给 OSD | **Ceph RBD** | OS + 镜像（不放 PVC） |

> 上 Ceph 却继续用 local-path，Kafka/Doris 的 PVC 会把系统盘撑爆；上 SeaweedFS 却把盘裸给 OSD，又没地方放 `/data`。二选一。

> 如果厂商只给"已格式化并挂载"的数据盘，Ceph 基本没戏（除非重新分区）。下单前问清楚：**数据盘是不是裸盘、能不能不格式化**。

## 五、环境随时会被释放，怎么把重建成本压到最低

这是本方案最关键的设计约束。按天买的实例，今天搭好、明天释放，下次 IP 全变、数据全没。对策不是"尽量别释放"，而是**假设它一定会没**。

### 五条原则

1. **环境即代码**：所有安装步骤进脚本，所有配置进 Git，不靠手工记忆。
2. **状态外置**：PG dump、values、镜像清单、kubeadm token 导出到本地/密码管理器，不放集群里。
3. **数据可再造**：测试数据用固定 seed 生成，不追求持久化；需要保留的只有"配置"和"结论"。
4. **分阶段可恢复**：脚本按 P0–P9 分阶段，每阶段幂等，断了从断点继续。
5. **一次会话 3–4 小时**：不追求一天干完，拆成两次，每次结束打快照/导出。

### 目录结构（建议放仓库 `deploy/`）

```
deploy/
├── inventory.env          # 三台机器的 IP/角色，不进 Git（或脱敏后进）
├── bootstrap.sh           # 入口：--phase 0..9，幂等
├── lib/common.sh          # 日志、等待、重试
├── phases/
│   ├── 00-host.sh         # 内核、时间、磁盘、防火墙
│   ├── 01-kubeadm.sh      # 三节点 kubeadm + CNI
│   ├── 02-base.sh         # OpenBao、Envoy Gateway、cert-manager
│   ├── 03-storage.sh      # SeaweedFS / Ceph、PostgreSQL
│   ├── 04-catalog.sh      # Polaris、bucket、warehouse
│   ├── 05-kafka.sh
│   ├── 06-doris.sh
│   ├── 07-compute.sh      # Spark、Flink
│   ├── 08-schedule.sh     # DolphinScheduler
│   ├── 09-governance.sh   # OpenMetadata、Prometheus 栈
│   └── 10-smoke.sh        # 端到端冒烟
├── values/                # 每个组件的 helm values
├── manifests/             # Kafka/Doris/Flink/Spark 的 CR
├── smoke/                 # 冒烟 SQL、生成数据脚本
├── export.sh              # 导出 PG dump、values、镜像清单
└── teardown.sh            # 清理 release / kubeadm reset
```

### 每次会话的标准动作

| 时点 | 动作 | 产物 |
| --- | --- | --- |
| 开始 | 买 3 台、记录 IP、改 `inventory.env` | 可连接的 3 台机器 |
| 阶段完成 | `./bootstrap.sh --phase N` | 幂等推进，失败可重跑 |
| 阶段验收 | `./smoke/phase-N.sh` | 通过/失败记录 |
| 结束前 | `./export.sh` + 云快照 | PG dump、values、镜像清单、快照 |
| 释放前 | `./teardown.sh`（可选） | 避免残留计费 |

### 下次重建要多久

| 场景 | 时间 | 说明 |
| --- | --- | --- |
| 快照可恢复 | 10–20 分钟 | 恢复 3 台快照、改 IP、起集群 |
| 快照不可用，脚本重建 | 1.5–2.5 小时 | 主要耗在拉镜像；脚本熟后更快 |
| 纯手工重搭 | 6–10 小时 | 就是这次要避免的 |

**结论：只要脚本和 values 在，重建是"半小时级"而不是"一天级"。** 这也是为什么第一天的产出必须是脚本，不是截图。

## 六、两次会话怎么排

如果只有一天，且中间有事，建议拆成两次（各 3–4 小时）：

### Session A：地基（约 3.5 小时）

```
买 3 台 → P0 体检 → P1 kubeadm 三节点 → P3 SeaweedFS + PG
→ P4 Polaris + Iceberg → Spark 写读冒烟 → export + 快照
```

产出：一个能跑 Iceberg 的三节点集群。这是整条链路里最难、最值得先固化的部分。

### Session B：计算与查询（约 3.5 小时）

```
恢复/重建 → P5 Kafka + Doris → P6 Flink → P9 端到端
→ P7 DS → P8 治理（可选）→ export + 快照
```

如果 Session A 后实例被释放、快照也没了：用脚本重跑 A（约 1.5–2 小时），再进 B。**所以 A 的脚本必须在第一次就写对、提交。**

## 七、成本账

| 项 | 方案 A（3×32C32G） | 方案 B（3×8C16G） |
| --- | --- | --- |
| 服务器 | ¥24/天 | ¥15/天 |
| 两次会话 | ¥48 | ¥30 |
| 快照 | 按厂商计价，通常几元 | 同 |
| 软件 | ¥0 | ¥0 |

即使按 3 天算，方案 A 也就 ¥72。相比"少买内存导致 OOM、多花一天排障"，这个钱值得花。

## 八、下单前问客服的 5 个问题

1. 三台能不能**同内网互通**？私网 IP 是否固定？
2. 数据盘是**裸盘**还是已格式化挂载？能不能不格式化给 Ceph 用？
3. 实例释放/到期后，**快照或自定义镜像是否保留**？保留多久、怎么计费？
4. 是否支持**按天计费**？关机是否仍计费？
5. 安全组能否**自定义内网端口**（6443/8472/10250/2379-2380/30000-32767）？

这 5 个问题的答案，直接决定"下次重建是 20 分钟还是 2 小时"。
