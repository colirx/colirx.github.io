# M7 推理与部署系统基础

**标签**：`milestone` `infra` `math`
**入口条件**：M6 的压测口径已建立（否则测出来的数字没有可比性）

> ⚠️ **本卡片已按你的实际硬件重写。** 原方案要求本地部署 vLLM —— 在你这台机器上
> **不可能完成**：AMD 官方支持表里 RX 6600 XT（gfx1032）的 **HIP SDK 一栏是 ❌**，
> vLLM 的 CPU 后端又要求 Linux。继续照原方案做，你会卡在第一步然后怀疑自己。
>
> **完整替代方案与成本估算见 [`docs/m7-inference-options.md`](../09.路线与资源/m7-inference-options.md)**，
> 硬件详情见 [`docs/environment.md`](../09.路线与资源/environment.md)。
>
> 一句话：**本地用 llama.cpp + Vulkan 做日常实验，vLLM 特有部分花几十块租 2–4 小时云 GPU 补上。**

## 你的机器能做什么、不能做什么

**实测配置**：i5-11400（6 核 12 线程）／ 48 GB 内存 ／ **AMD Radeon RX 6600 XT 8GB** ／ D 盘可用 100 GB

| 能不能 | 说明 |
|---|---|
| ❌ **vLLM** | 官方不支持 Windows，且不支持 AMD 消费级显卡。**这条路是死的，不要浪费时间试。** |
| ✅ **llama.cpp + Vulkan 后端** | AMD 显卡在 Windows 上唯一靠谱的 GPU 加速路径。本里程碑的主力工具。 |
| ✅ **llama.cpp 纯 CPU** | 48GB 内存足够跑 7B–14B 量化模型，用来做"CPU vs GPU"对照正好。 |
| ⚠️ **WSL2 + ROCm** | RX 6600 XT 是 gfx1032，ROCm 官方只正式支持 gfx1030（6800/6900）。**不可靠，不推荐。** |
| ❌ **多卡／张量并行／PD 分离** | 单卡，无从验证。 |

**你能拿到真实数据的**：吞吐（tok/s）、首 token 延迟（TTFT）、P95/P99 延迟、
量化档位对照（Q4_K_M / Q5_K_M / Q8_0 的显存、速度、质量三方差）、并发与批处理
（`llama-server --parallel`）、KV cache 与上下文长度的内存关系、CPU 与 GPU 的差异。

**你拿不到实测数据的**：vLLM 的 PagedAttention 效果、连续批处理调度、PD 分离、
张量并行、多机推理。**这些改为「读 + 算」，不算你动手做过**——写报告时必须标注清楚。

> **一个务实建议**：你在「数据与人工智能处」，单位大概率有带 GPU 的服务器。
> 如果合规允许，M7 的 vLLM 部分**申请那台机器跑**，比你本地硬撑有价值得多。
> 但不要把计划建立在"也许能申请到"上——本卡片默认按本地设备设计。

## 能力目标

用**自己测出来的**吞吐、延迟、内存数据做部署选型决策，
并能诚实区分「我测过的」和「我读来的」。
完成后你不会再问"该用哪个模型"，而是先问"什么场景、什么约束、多少预算"。

## 任务

1. **踩通环境（一次性）**：编译或用预编译包跑起 `llama.cpp`，
   分别验证 **Vulkan（GPU）** 和 **纯 CPU** 两条路径都能跑通。
   记录：编译/下载了什么、版本号、踩了什么坑。产出 `docs/labs/M7-环境踩坑.md`。
2. **拉通端到端**：用 `llama-server` 暴露 OpenAI 兼容接口，
   把 M3 的 Agent 指到本地服务并跑通同一批任务。
   **要求：Agent 侧零代码改动，只改 base_url** ——做不到说明接口抽象没做好。
3. **量化对照实验**：同一模型（建议 7B–8B 级别，Q4 约 4–5 GB，D 盘放得下）
   跑 Q4_K_M / Q5_K_M / Q8_0 三档，测：模型体积、内存占用、tok/s、TTFT、
   **以及质量分（用 M2 的评测器测）**。三档都要有数字。
4. **并发与长上下文压测**：用不同 `--parallel` 值和不同上下文长度（4K / 8K / 16K）
   画并发—吞吐—延迟曲线。**必须记录 P95/P99，不许只报平均。**
   同时验证 KV cache 的内存占用随上下文长度如何变化，和你的手算值对照。
5. **写选型报告**：`docs/adr/M7-推理选型.md`。给定"某类业务场景 + 成本约束 + 延迟要求"，
   给出推荐与拒绝理由，全部以任务 3/4 的数据为据。
   **必须单独一节写「我这台机器测不了的，以及为什么」**。

> 任务数超过 2–4 个是刻意的：本里程碑硬件限制大，步骤必须拆细才走得动。

## 验证标准

- [ ] llama.cpp 的 GPU 与 CPU 两条路径都跑通，版本号与启动参数记录在案
- [ ] M3 的 Agent 只改 base_url 就切到本地服务，行为一致
- [ ] 三个量化档的 **体积／内存／tok/s／TTFT／质量分** 五个数字齐全
- [ ] 并发曲线至少 3 个并发档位，含 P95
- [ ] KV cache 实际内存占用与你的手算值对照，差异有解释
- [ ] 选型报告的结论能被他人用同样硬件复现
- [ ] **报告里有明确的「未实测」清单**，没有把读来的数据包装成自己的

## 数学 / 原理概念

- **浮点数与量化**：精度损失发生在哪，为什么 4bit 常常"够用"（闸门 5 已覆盖）
- **矩阵乘法与显存带宽**：为什么大模型推理常常是访存瓶颈而非算力瓶颈
- **KV Cache 显存估算**：能自己估出某个模型某个上下文长度的内存需求（**手算一次，再用实测对照**）
- **吞吐—延迟权衡**：为什么 batch 变大吞吐升而延迟恶化
- **排队论直觉**：为什么利用率接近 100% 时延迟会爆炸
