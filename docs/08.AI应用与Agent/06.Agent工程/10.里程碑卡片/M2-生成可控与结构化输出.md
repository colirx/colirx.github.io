# M2 生成可控与结构化输出

**预计投入**：25 小时
**标签**：`milestone` `agent` `eval` `math`
**入口条件**：M1 的检索链路可作为生成阶段的稳定输入。

## 能力目标

让模型的输出从"一段看起来不错的话"变成"一个下游程序能安全消费的结构"；
并且能度量生成质量、定位幻觉发生在哪一步。

## 任务

1. **结构化输出**：在 `src/generation/` 实现带 schema 约束的输出
   （JSON schema / 工具调用约束），处理解析失败与重试。
   要求：解析失败率与重试次数进日志。
2. **建生成评测**：写一个 LLM-as-judge 评测器，对固定问题集打分
   （相关性、忠实度、完整性），并用人工抽检校准它——**judge 必须先被验证才可用**。
3. **失败案例库**：把幻觉、答非所问、过度冗长的案例逐条存进 `docs/labs/M2-failures.md`，
   标注属于"检索没给到"还是"给到了但没用好"。
4. **反幻觉手段实测**：至少实现两种（如强制引用来源、无依据则拒答、要求逐句给出处），
   用任务 2 的评测器量化效果。

## 验证标准

- [ ] 结构化输出在 200 次连续调用中解析失败率为 0（含重试后的最终成功率）。
- [ ] judge 评分与人工抽检的一致率可量化，并记录不一致的样例与原因。
- [ ] 至少 15 条失败案例入库，其中 ≥5 条能定位到具体环节。
- [ ] 反幻觉手段带来的效果提升有数字，且给出它对延迟/成本的影响。

## 数学 / 原理概念

- **概率与采样**：temperature、top-p 到底在改什么（可跳过，自测后决定）
- **期望与方差**：为什么单次评测结果不可信，为什么要跑多次取分布
- **交叉熵直觉**：模型"置信度"和它实际正确率的关系，以及为什么不能直接当阈值用
- **校准（calibration）**：模型说 90% 把握时，真的对 90% 吗

## 外部资源（限 1 个）

- 《Judging LLM-as-a-Judge》（MT-Bench 那篇）——**用在任务 2**。
  解决的问题：直接写出一个会系统性偏袒长回答、偏袒第一个选项的 judge 是常见事故；
  这篇给出位置偏差、长度偏差的具体表现和缓解做法，避免你的评测器本身成为误差来源。
