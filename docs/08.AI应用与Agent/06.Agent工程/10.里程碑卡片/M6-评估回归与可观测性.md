# M6 评估、回归与可观测性

**预计投入**：30 小时
**标签**：`milestone` `infra` `eval` `math`
**入口条件**：M3/M5 的轨迹日志已存在；本里程碑可与 M2 并行启动，收口在 M5 之后。

## 能力目标

把 Agent 系统当成一个线上服务来管：
任何一次改动都能自动跑评测、给出回归结论，并且线上出问题时能定位到具体环节。

## 任务

1. **全链路埋点**：按 span 结构记录（一次会话 → 一次 Agent 循环 → 一次模型调用 → 一次工具调用），
   字段统一。参考 OpenTelemetry 的 GenAI 语义约定，别自创字段名。
2. **回归测试与 CI**：把 M1/M2/M5 的评测集接进 CI，每次 push 自动跑，
   输出"相比基线，哪些指标退化"。
3. **成本与延迟看板**：按任务类型、按工具维度聚合 token 与耗时，找出成本大头。
4. **故障演练**：人为注入三类故障（模型超时、工具返回脏数据、检索为空），
   验证能否从 trace 中一眼定位，并补上缺失的日志。

## 验证标准

- [ ] 一次代码改动推到仓库后，自动跑完评测并在 PR 上给出回归结论。
- [ ] 给定一个失败的线上会话 ID，能在 5 分钟内定位到是检索、生成还是工具的问题。
- [ ] 看板能回答"上个月哪类任务最贵"，且数字与账单可对账。
- [ ] 三类注入故障全部被 trace 捕获，无静默失败。

## 数学 / 原理概念

- **均值与方差**（可跳过，自测后决定）
- **置信区间直觉**：为什么评测集只有 30 条时，"提升了 3%" 可能毫无意义
- **抽样偏差**：评测集怎么选才不像"只测自己会的"
- **分布与长尾**：为什么 P99 延迟比平均延迟更值得盯

## 外部资源（限 1 个）

- OpenTelemetry GenAI 语义约定（semantic conventions）——**用在任务 1**。
  解决的问题：字段命名一旦自创，后续接入任何观测平台都要重写；
  按约定埋点，等于免费获得一套业界通用的字段与工具兼容性。
