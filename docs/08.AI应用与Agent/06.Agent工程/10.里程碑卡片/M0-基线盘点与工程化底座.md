# M0 基线盘点与工程化底座

**预计投入**：20 小时
**标签**：`milestone` `infra` `math`
**入口条件**：M-1 完成，**或 M-1 用满 30 小时封顶**（后者同样可以开始，不必卡住）
**标签补充**：这是唯一一个允许"造轮子"的里程碑，目的是摸清 Dify 替你做了什么。

## 能力目标

脱离 Dify，用纯代码跑通一条完整的检索问答链路，并拥有一个可复用的评测脚本骨架。
完成后你能回答："Dify 在这个环节到底做了什么？如果让我自己写，代价是什么？"

## 任务

1. **盘点现有资产**：挑一个你在单位里真实在用的 Dify RAG 应用，把它的流程一步步写下来
   （输入 → 切分 → 检索 → 拼 prompt → 生成 → 输出），标注每步的输入输出格式与模型调用点。
   产出：`docs/adr/M0-盘点-现有Dify链路拆解.md`。
2. **纯代码重写最小版**：用 Python 把上述链路重写一遍（允许调 API，不允许用框架），
   落在 `src/retrieval/` 与 `src/generation/`。要求：配置与代码分离、结构化日志、
   每次调用记录 token 与耗时。
3. **建评测脚本骨架**：在 `src/eval/` 写一个执行器，读 `eval/datasets/*.jsonl`，
   跑一遍问答，输出结构化结果（问题、检索到的文档、答案、耗时、成本）。
   此时指标可以是空的，但**接口要定型**。
4. **固化仓库工程习惯**：写 `docs/adr/` 的决策模板、commit 规范落地、跑通第一次提交。

## 验证标准

- [ ] 在没有 Dify 的环境里，用一条命令跑通一次带检索的问答，输出结构化日志。
- [ ] 同一份输入重复运行两次，检索结果一致（可复现），差异只出现在生成阶段。
- [ ] 评测执行器能对 5 条手工样例输出结果表，字段包含耗时与成本。
- [ ] 能用一分钟向同事讲清"我这条链路和 Dify 那条链路的差别在哪"。

## 数学 / 原理概念

- **向量、点积、余弦相似度**（可跳过，自测后决定——做过后端/大数据大概率接触过）
- **embedding 与维度**：为什么维度影响存储与召回
- **Token 与分词**：为什么"成本"和"上下文长度"都以 token 而非字符计
