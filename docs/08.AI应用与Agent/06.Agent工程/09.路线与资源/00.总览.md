# Agent Engineering Path

从「AI 应用开发者」到「AI 系统工程师」的里程碑式学习工程库。

本仓库不是教程合集，是**一份长期工程档案**：每个里程碑的能力目标、任务、验证标准、
数学直觉补课点，以及全部实操产出（代码、实验报告、评测数据、架构决策记录）。

---

## 1. 起点与终点

- **起点**：5 年工程经验（Java / 大数据 / 全栈），在用 Dify 做 RAG 与 Agent 应用。
- **终点**：具备 Agent 系统工程能力——能把 Agent 系统设计、度量、优化、部署、运维；
  达到能进入前沿 AI 公司工程团队的深度。
- **纪律**：不排周次、不排日期。按里程碑推进，每个里程碑以**可验证的产物**收口。
  允许中断、允许长时间停摆，恢复时从 PROGRESS.md 的未勾选项继续。

## 2. 主线与辅线

**主线：Agent 工程能力。** M0 → M8 依次是「工程底座 → 检索 → 生成可控 → Agent 循环 →
上下文与记忆 → 多步编排 → 评估与可观测 → 推理部署 → 作品化」。
每一环都在上一环的产物上叠加，不存在"推翻重来"。

**辅线：数学直觉。** 分两段，**不是"先学完数学再学工程"**：

- **前段（M-1）**：一段**按内容闸门推进**的前置补给，目标是"能读懂工程材料"而不是掌握数学。
  五个闸门，**判据是「不看资料能用自己的话讲清」而不是「看完」**；
  讲不出来就把概念记进「待补」清单**继续前进**，绝不原地重看第三遍。
- **后段（M0 起）**：不单独排期。每个里程碑只列该阶段**工程上真正会用到**的概念，
  遇到就补一页 `docs/math-notes/` 笔记，用代码或图示验证直觉，不求推导与证明。
  每个概念标注是否「可跳过，自测后决定」——有大数据背景的话大概率能跳过一半。

判断标准只有一条：**能不能用手上的代码解释这个概念在解决什么问题**。
做不到就说明没补上，但也不打断当前任务——记进笔记，继续推进。

- 学习资源（中文视频为主）：[`learning-path.md`](learning-path.md)
- 硬件与环境约束：[`environment.md`](environment.md) ← **哪些任务真能做，以它为准**
- 成果登记：[`deliverables.md`](deliverables.md) ← **这一页才是给别人看的**

## 3. 里程碑总览

| 编号 | 名称 | 能力目标（完成后我能做什么） | 预计投入 |
|---|---|---|---|
| M-1 | 数学直觉补给站（前置） | 看到工程材料里的数学符号不再卡住；10 个核心概念能用自己的话+代码解释 | **五个内容闸门**，不按小时 |
| M0 | 基线盘点与工程化底座 | 脱离 Dify 用纯代码跑通一条可复现的检索问答链路，并拥有评测脚本骨架 | 20h |
| M1 | 检索质量工程 | 对检索做定量评测与调优，用数据而非手感决定切分/embedding/重排 | 30h |
| M2 | 生成可控与结构化输出 | 约束模型输出结构，度量生成质量，定位并压低幻觉 | 25h |
| M3 | Agent 循环与工具调用 | 不依赖框架从零实现 tool-calling 循环，含重试、超时、成本统计 | 40h |
| M4 | 上下文工程与记忆 | 长任务中上下文不爆窗口、不丢信息，成本可预测 | 35h |
| M5 | 多步任务编排 | 判断什么该拆、什么不该拆，并用 A/B 数据支撑这个判断 | 35h |
| M6 | 评估、回归与可观测性 | 把 Agent 当生产服务管：全链路 trace、回归测试、成本延迟看板 | 30h |
| M7 | 推理与部署系统基础 | 用真实吞吐/延迟/显存数据支撑部署选型与优化决策 | 40h |
| M8 | 前沿对齐与作品化 | 有可对外展示的工程作品，能复现前沿技术报告中的组件 | 40h+ |

合计约 325 小时以上，不含 M8 的持续投入。

## 4. 目录结构

```
agent-engineering-path/
├── README.md                 # 本文件：计划总览
├── PROGRESS.md               # 进度看板：唯一需要频繁更新的文件
├── docs/
│   ├── learning-path.md      # 学习路径：中文视频/文档清单，按知识点绑定用途
│   ├── environment.md        # 硬件与环境约束：哪些任务这台机器真能做
│   ├── deliverables.md       # 成果台账：每个产物的位置与验证数据
│   ├── templates/            # 每个里程碑"具体要写什么"的填空模板
│   ├── milestones/           # M-1, M0..M8 详细卡片（每个对应一个 GitHub issue）
│   ├── math-notes/           # 数学直觉笔记，一概念一页，含 _TEMPLATE.md
│   ├── labs/                 # 实验报告：假设 → 方法 → 数据 → 结论，含 _TEMPLATE.md
│   └── adr/                  # 架构决策记录：选了 A 为什么不是 B，含 _TEMPLATE.md
├── src/                      # 真实代码，按能力域分包
│   ├── retrieval/            # 切分、索引、检索、重排
│   ├── generation/           # 结构化输出、prompt 组装
│   ├── agent/                # 循环、工具、上下文管理、记忆
│   ├── eval/                 # 评测指标与评测执行器
│   └── serving/              # 推理服务、压测、部署
├── eval/datasets/            # 评测集（问题、标准答案、golden 文档）
└── ops/
    ├── labels.md             # issue 标签体系与使用规则
    ├── bootstrap-github.ps1      # 一键补齐 GitHub 侧（gh CLI 版）
    ├── bootstrap-github-rest.ps1 # 同上，纯 REST，不需要装 gh
    └── manual-steps.md       # 无法自动执行时的人工操作清单
```

三个 `_TEMPLATE.md` 不是装饰：**没有模板，`docs/labs/` 和 `docs/adr/` 会一直是空的。**

## 5. 工作方式

1. 每个里程碑 = 一个 GitHub issue，标题 `[Milestone X] 名称`，正文即 `../10.里程碑卡片/` 对应文件。
2. 每个任务 = issue 正文里一个 checkbox；完成时打勾并附 commit 链接。
3. 交付物进 `src/` 或 `docs/labs/`，用 commit 记录推进，commit message 带里程碑前缀（见 `ops/labels.md`）。
4. 出现选型分歧时写 `docs/adr/`，不写进聊天记录里等它烂掉。
5. 里程碑收口时，在 `PROGRESS.md` 记录：投入小时、验证结果、下一个里程碑的入口条件。
