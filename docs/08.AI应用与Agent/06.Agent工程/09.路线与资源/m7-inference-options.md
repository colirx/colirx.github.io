# M7 推理方案选型：本机跑不了 vLLM 怎么办

> 结论先行：**llama.cpp + Vulkan 覆盖 M7 约 80% 的学习目标；
> 剩下 20% 的 vLLM 特有部分，租 2–4 小时云 GPU 解决，比在本机折腾任何替代品都划算。**

---

## 一、先说清本机为什么堵死

**你的显卡：AMD Radeon RX 6600 XT（RDNA2 / gfx1032 / 8GB）**

我查了 AMD 官方文档的 Windows 支持表，原文是这样的：

| 名称 | 架构 | LLVM target | Runtime | HIP SDK |
|---|---|---|---|---|
| AMD Radeon RX 6600 XT | RDNA2 | gfx1032 | ✅ | **❌** |

**HIP SDK 那一栏是 ❌**——意味着没有官方预编译库，PyTorch-HIP 走不通。
（对比：RX 6800/6900 是 gfx1030，HIP SDK 栏是 ✅。差的不是性能，是官方支持级别。）

而 **vLLM 的 CPU 后端官方要求是 `OS: Linux`**，且 BF16 是默认数据类型、
推荐 AVX-512 指令集。加上 vLLM 本身不支持 Windows——

**所以「本机 + Windows + 这张卡」这个组合，vLLM 是无解的。** 不要在这上面花时间。

---

## 二、五个可选方案

| 方案 | 能拿到什么 | 拿不到什么 | 代价 | 推荐度 |
|---|---|---|---|---|
| **llama.cpp + Vulkan** | tok/s、TTFT、P95、量化对照、并发、**KV cache 量化**、投机解码、CPU/GPU 对照 | vLLM 的 PagedAttention 与调度实现 | 需编译或找预编译包，参数多 | ⭐⭐⭐⭐⭐ |
| **Ollama** | 快速得到 OpenAI 兼容服务；能跑通端到端 | 实验控制力弱（可调参数少，量化档位固定） | 几乎为零 | ⭐⭐⭐（只作练手） |
| **LM Studio** | 图形界面 + 本地 API；适合先建立手感 | 不可脚本化重复测量 | 低 | ⭐⭐（新手向） |
| **PyTorch + DirectML** | 能跑原生 HF Transformers 模型（而非 GGUF） | 生态处于维护模式，新版本 PyTorch 支持滞后 | 中高，坑多 | ⭐⭐ |
| **vLLM CPU 后端**（WSL2/VM 内） | **能真实看到 vLLM 的接口、调度与日志** | 性能数据（慢到不能作为结论）；需要 Linux | 中，要编译 | ⭐⭐⭐（只为看行为） |
| **租云 GPU 跑 vLLM** | **PagedAttention、连续批处理、张量并行、PD 分离的全部真实数据** | 长期可用性（按小时计费） | **几小时几十元** | ⭐⭐⭐⭐⭐ |

## 三、首推方案的细节：llama.cpp + Vulkan

### 为什么它能覆盖 M7 的大部分目标

M7 要的是「用**自己测出的**吞吐、延迟、内存数据做决策」，而不是「用过 vLLM 这个软件」。
llama.cpp 在这一点上完全够用，而且有些实验比 vLLM 更好做：

| M7 要测的 | llama.cpp 对应能力 |
|---|---|
| 吞吐 tok/s、TTFT、P95/P99 | `llama-server` 自带 `/metrics` 与计时日志 |
| 并发与批处理 | `--parallel N` 多槽并发；`-b` / `-ub` 控制批大小 |
| 量化档位对照 | GGUF 的 Q4_K_M / Q5_K_M / Q8_0 / F16 直接换文件 |
| **KV cache 内存随上下文变化** | `-c` 设上下文长度，实时观察内存占用 |
| **KV cache 量化** | `--cache-type-k` / `--cache-type-v`（如 `q8_0`）——**vLLM 里这个实验反而更麻烦** |
| 显存 vs CPU 对照 | `-ngl N` 控制多少层放 GPU，可以从 0 调到全部 |
| Flash Attention 影响 | `-fa` 开关 |
| 投机解码 | `--model-draft` 指定草稿模型 |
| OpenAI 兼容接口 | `llama-server` 暴露 `/v1/chat/completions`，M3 的 Agent 只改 base_url |

> 参数名以 `llama-server --help` 为准，版本间会变。**把实际用的版本号和完整命令记进报告。**

### 安装路径（按成功率排序）

1. **预编译包**（最省事）：llama.cpp 的 releases 页面提供 Windows 二进制，
   注意选 **Vulkan** 或 **AVX2** 变体。先跑通再谈优化。
2. **自行编译**：需要 CMake + Visual Studio Build Tools。
   编译开销大，但能拿到最新特性和最好的 Vulkan 支持。
3. **WSL2 内编译**：路径更接近 Linux 生态，但 Vulkan 需要额外配置，**不推荐作为首选**。

### 模型怎么选（按你的 100GB D 盘）

| 规模 | Q4_K_M 体积 | 建议 |
|---|---|---|
| 7B–8B | 约 4–5 GB | **主力**。三档量化加起来约 20 GB，跑得动、测得快 |
| 14B | 约 9 GB | 有余力再加，用来观察规模对延迟的影响 |
| 32B | 约 19–20 GB | **不要一开始就上**，8GB 显存装不下，CPU 推理会慢到挫伤积极性 |

## 四、vLLM 那 20% 怎么办：租云 GPU

**这是本文件最重要的一条建议。**

你要从 vLLM 拿到的东西里，有三样 **llama.cpp 永远给不了**：

1. **PagedAttention 的实际效果**（显存碎片、块级 KV 管理）
2. **连续批处理的调度行为**（新请求如何插队、吞吐随并发怎么变）
3. **张量并行与 PD 分离**（单卡无从验证，至少需要 2 张卡）

这三样都是**原理级理解**，靠读能懂 80%；但剩下 20%「亲手跑一次」的价值，
远超在本地用别的工具假装。

**做法**：在国内云平台按小时租 1–2 张 4090/A10 级别显卡，Linux 镜像，
**跑 2–4 小时**，把 M7 卡片里 vLLM 特有的部分集中做完：

- `vllm serve` 起服务，观察日志里的 block 分配
- 用官方 benchmark 脚本扫并发，拿到连续批处理的吞吐曲线
- 用 `--tensor-parallel-size 2` 跑一次张量并行
- 有条件的话跑一次 PD 分离

按小时计费，单次成本是**几十元量级**（具体以平台实际报价为准）。
**这比买显卡便宜三个数量级，比永远不碰 vLLM 有价值得多。**

> **另一条更省的路**：你在「数据与人工智能处」，单位可能有 GPU 服务器。
> 若合规允许，申请一次环境跑这些实验。**但不要让计划依赖"也许能申请到"。**

## 五、明确拿不到的（必须在报告里标注）

M7 的验收标准里有一条硬要求：**报告必须有「未实测」清单**。以下是预填内容：

- [ ] PagedAttention 的显存碎片效果 —— 本机无 NVIDIA，无法验证
- [ ] 连续批处理调度行为 —— 本机方案是槽位并发，机制不同
- [ ] 张量并行 —— 单卡
- [ ] PD 分离 —— 单卡
- [ ] 多机推理 —— 无

**处理方式**：能读懂的写"读来的，来源是 X"；读不懂的写"待云 GPU 实验补充"。
**不要把读来的数据包装成自己测的**——这在这份报告里比数字不对更严重。

---

## 六、一句话总结

**日常实验用 llama.cpp + Vulkan（本地、免费、可控）；
vLLM 特有部分花几十块租几小时云 GPU 补上；
两者都覆盖不了的，如实写进「未实测」清单。**
